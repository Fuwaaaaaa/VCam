## Process highlights

### 1. Phase 0 ゲートが正しく機能

T-004 の事前検証テスト 1 つで仮説 falsified。「OneEuroFilter は同値連続呼出
で derivative 退化しない」ことが証明され、計画の `git rm T-004` ロールバック
条件発動。**~10 ファイルの無駄な refactor を回避**。

教訓: Phase 0 / Go-No-Go ゲート方式は実装コスト ≪ 検証コストの場合に高 ROI。

### 2. ブランチ戦略の動的調整

途中で `origin/main` が `gone` であり `feature/vite-migration` が de facto default
であることが判明。当初の `→ main` PR 計画を `→ feature/vite-migration` に切替。
`gh pr create` のエラーで気付けた (もし強行していたら local main も更新して
混乱を増やしていた)。

教訓: PR 作成前に `gh repo view --json defaultBranchRef` を 1 回叩くだけで
分かる。今後デフォルトブランチ前提のフローを書く際の hook 候補。

### 3. PR の粒度を意識的に分割

T-001 を 1 PR にせず 3 PR (#3 scaffold / #4 research / #6 checklist) に分割。
各 PR の review 単位が「レビュー可能な大きさ」で、merge 順序の柔軟性も確保。
PR #5 (release bump) は完全に独立、PR C (実 VRM) との conflict なし。

### 4. 人手 vs Claude の境界を明示

T-001 PR C は「ライセンス確認 + バイナリ取得」が必要なため Claude では完結
不能。代わりに調査 (#4) + チェックリスト (#6) で人手側のコストを最小化。
"VRM を選んで取得する" → "AvatarSample_F.vrm をダウンロードして実行" まで
落とし込んだ。
